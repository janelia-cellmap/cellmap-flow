cellmap_flow.models.resolve
===========================

.. py:module:: cellmap_flow.models.resolve

.. autoapi-nested-parse::

   A model from whatever reference a user has in hand, without knowing the model types.

   ``resolve(ref)`` turns a path, a URL, a Hugging Face repo, a zoo nickname or
   a Cellpose model name into a ``Resolved``: the model type, its constructor
   arguments, a name, and what the user must still give. ``Resolved.entry()``
   is the model entry that ``registry.build_model`` (and so a YAML's
   ``models:``) takes. The dashboard's ``POST /api/models/resolve`` and
   ``cellmap_flow add`` answer with it.

   The checks, in this order; the first that matches wins. Each is cheap: a
   stat, a file name, a regex, or (only when ``online``) one request.

   1. A local file or folder (``~`` expanded; the entry gets its absolute path):

      - a ``.py`` file: ``script``;
      - a folder with ``metadata.json``: ``cellmap`` (a cellmap-models export,
        which is served from its ``model.ts``);
      - a folder with a mia-train model's ``config.json`` and
        ``model.safetensors`` (cellmap_models' ``MIA_FILES``) whose config
        cellmap_models can serve (``is_mia_config``): ``mia``; with any other
        config.json (a pretraining checkpoint's, or no mia-train model's at
        all), the folder is whatever the checks below make of it;
      - a folder with ``rdf.yaml`` or ``bioimageio.yaml``, such a file itself
        (``*.rdf.yaml`` too), or a ``.zip`` with one inside: ``bioimage``;
      - ``model_checkpoint_<n>``, a ``.ts`` or a ``model.pt``: ``fly``, which
        reads the channels and voxel sizes from the files beside it; what it
        cannot find is reported in ``needs``;
      - a folder with ``adapter_config.json`` (a PEFT LoRA adapter), or a full
        finetune's ``model_state_dict.pt``: ``finetune``, which needs its
        ``base_model``;
      - Cellpose-SAM weights (Cellpose 4 saves a torch state dict without an
        extension; its keys say what it is): ``cellpose``;
      - an ``.onnx`` file: ``onnx``. One the browser finetuned carries its
        manifest, which says its geometry; any other needs its voxel size.

   2. A prefix, to say outright what a reference is: ``hf:org/repo[@revision]``
      (``hf:org/repo/folder``: that folder's ONNX web export),
      ``bioimageio:<id, nickname, URL or path>``, ``cellpose:<name or path>``,
      ``fly:<path>``, ``dacapo:<run>@<iteration>``, ``script:<path>``,
      ``onnx:<path, folder or org/repo/folder>``, ``mia:<org/repo[@revision] or
      folder>``. The type's own name works as
      its prefix too (``huggingface:``, ``bioimage:``). Nothing after a prefix
      is looked up online.

   3. A Cellpose model name (``cpsam_v2``, ``cpsam``, ``cpdino``,
      ``cpdino-vitb``): ``cellpose``.

   4. A URL: a bioimage.io model page, a Zenodo record, a DOI link, a Hypha
      artifact or the URL of an ``rdf.yaml`` or zip: ``bioimage``;
      ``huggingface.co/<org>/<repo>`` (``/tree/<revision>`` too): as 5, and
      with a folder after the revision (``/tree/main/setup_54``, or a file in
      it), as 5's ``org/repo/folder``.

   5. ``org/repo/folder`` (``@revision`` optional): a folder of a Hugging Face
      repo of ONNX web exports, as cellmap/onnx-web-models holds them, one
      model a folder with its ``manifest.json``: ``onnx``. ``org/repo``
      (``@revision`` optional; not a DOI, which is 7's): a Hugging Face repo.
      Online, its file list is read: with ``metadata.json`` and ``model.ts`` it
      is a cellmap-models export, ``huggingface``; without ``metadata.json`` but
      with a mia-train model's files, its ``config.json`` is read too (a few
      kB) and the repo is ``mia`` when cellmap_models can serve that config
      (``is_mia_config``), else answered as any other repo is; a repo of web
      exports is refused with its folders, one of which to add; anything else
      is refused with what to do instead. A model a server published has both: the
      export at the root, which ``org/repo`` serves (only the root's files are
      downloaded), and its web export in a folder, ``org/repo/folder``. Offline, or when the Hub cannot be reached,
      either is taken to be what it looks like, with a note.

   6. A BioImage Model Zoo id or nickname (``affable-shark``,
      ``10.5281/zenodo.5764892``): ``bioimage``. Online, it is looked up in
      the zoo's model list; offline, a nickname- or DOI-shaped one is taken to be
      one, with a note.

   7. A folder of cellmap/onnx-web-models by its name (``setup_54``), online
      only: ``onnx``.

   Anything else is a ValueError that says what was tried.

   Importing this module imports only the standard library (and
   ``models.entry``, which has no more). Resolving imports
   the model config classes (numpy and funlib, as the registry does), the
   online checks huggingface_hub, and a mia-train model's check cellmap_models'
   ``model_export.mia_model`` (which imports torch, never mia-train); nothing
   else imports torch or a model's framework, and ``Resolved.entry()`` is a
   plain dict.

.. py:class:: Resolved

   What a reference resolved to.

   .. attribute:: type

      the model type's name (``registry.model_types``).

   .. attribute:: params

      its constructor arguments, as a YAML entry gives them.

   .. attribute:: name

      the model's name: the one asked for, else one from the reference.

   .. attribute:: env

      the type's default environment for this model (``default_env``),
      for display; None runs it in cellmap-flow's own. Not in ``entry()``.

   .. attribute:: how

      one line saying what the reference was taken to be.

   .. attribute:: needs

      constructor arguments the user must still give (a key of
      ``params`` once given), e.g. ``voxel_size`` for Cellpose.

   .. attribute:: notes

      anything else worth saying: what was assumed, or ignored.

   .. py:method:: to_json() -> Dict[str, Any]

      Every field, as the dashboard's route answers with them.



.. py:function:: resolve(ref: str, *, name: str = None, voxel_size=None, online: bool = True) -> Resolved

   The model ``ref`` refers to (see the module docstring for the checks, in order).

   :param ref: what the user pasted.
   :param name: the model's name; by default one is made from ``ref``.
   :param voxel_size: nm per voxel (one number, one per axis, or "8,8,8"):
                      given to Cellpose and bioimage.io models as ``voxel_size`` and to
                      a fly model (and an onnx one without a manifest) as
                      ``input_voxel_size``; any other model is run at it, as its
                      entry's ``run_voxel_size`` (``ModelConfig.run_voxel_size``),
                      unless it reads its input itself (a script with its own
                      ``process_chunk``), which ignores it with a note.
   :param online: whether a Hugging Face repo or zoo id may be checked online.

   :raises ValueError: ``ref`` is none of the things checked, or is one that
       cellmap-flow cannot serve; the message says which and why.


.. py:data:: MIA_MODULE
   :value: 'cellmap_models.model_export.mia_model'


.. py:function:: mia_model()

   cellmap_models' ``model_export.mia_model``, imported now (it imports
   torch, never mia-train). The one loader of it: resolving asks it which
   references are mia-train models, the mia type (configs/mia.py) what they
   are and how to export them.

   :raises ImportError: the cellmap_models installed has none.


.. py:function:: servable_mia_config(config) -> bool

   Whether cellmap_models can serve the mia-train model whose
   ``config.json`` is ``config`` (``is_mia_config``: a segmentation network,
   not a pretraining checkpoint). False for any other config.json, and with
   a cellmap_models that has no mia_model. What makes a repo or a folder a
   mia model, here and in the Hugging Face listing (hf_catalog).
