Viewer layer API

A running dashboard can add, rename and remove layers of its Neuroglancer viewer over HTTP, so a script or a shell can put a dataset next to the predictions without restarting anything. The dashboard’s own pages don’t use these routes. It can also set the pipeline the predictions are drawn through, as the pages do.

Every layer route takes a JSON POST body and answers with {"success": true, ...}, or {"success": false, "error": "..."} and a 4xx or 5xx status. Open the dashboard’s Neuroglancer tab again (or reload it) to see a change when the answer says "reload_page": true.

In the examples, DASHBOARD is the address you open the dashboard at, the Running on http://... line it prints when it starts:

DASHBOARD=http://10.36.1.20:43219

Add an image layer

path is a zarr or n5 array or multiscale group, or a precomputed:// URL, opened the same way as the raw dataset (see Data paths). shader and blend are optional and passed to Neuroglancer as they are. A layer with the same name is replaced.

curl -X POST "$DASHBOARD/api/viewer/add-image-layer" \
     -H 'Content-Type: application/json' \
     -d '{"path": "/path/to/dataset.zarr/em/fibsem-uint8",
          "name": "em", "blend": "additive"}'

Add a segmentation layer

The same, for label volumes. disable_meshes turns off Neuroglancer’s on-the-fly meshes, which can take a lot of the dashboard’s memory for a large label volume.

curl -X POST "$DASHBOARD/api/viewer/add-segmentation-layer" \
     -H 'Content-Type: application/json' \
     -d '{"path": "/path/to/segmentation.zarr/mito",
          "name": "mito", "disable_meshes": true}'

Rename a layer

The layer keeps its place in the layer list. It answers 404 when old_name isn’t a layer and 409 when new_name already is one.

curl -X POST "$DASHBOARD/api/viewer/rename-layer" \
     -H 'Content-Type: application/json' \
     -d '{"old_name": "mito", "new_name": "mito (v2)"}'

Remove a layer

Removing a layer that isn’t there is not an error; the answer says "removed": false.

curl -X POST "$DASHBOARD/api/viewer/remove-layer" \
     -H 'Content-Type: application/json' \
     -d '{"name": "mito (v2)"}'

A layer’s shader settings go with it when it is renamed and are dropped when it is removed, so a new layer with the old name starts from the defaults.

The routes open any path the dashboard’s user can read, as the dashboard’s “set data” does, and anyone who can reach the dashboard can call them.

Set the pipeline

PUT /api/pipeline sets the input normalization and postprocessing chains, and redraws the raw data and every prediction layer through them. It is what Submit on the dashboard page sends, and what the pipeline builder sends after each edit. Each chain is a list of steps in the order they run, each step an op’s class name and its parameters; send [] for none.

curl -X PUT "$DASHBOARD/api/pipeline" \
     -H 'Content-Type: application/json' \
     -d '{"input_norm": [{"name": "MinMaxNormalizer", "min_value": 0, "max_value": 255},
                         {"name": "LambdaNormalizer", "expression": "x*2-1"}],
          "postprocess": [{"name": "ThresholdPostprocessor", "threshold": 0.5}]}'

The answer is {"success": true, "pipeline": {...}, "digest": "...", "layers": [...]}: the chains as set, the digest that names the layers’ source, and the prediction layers redrawn. A model whose server has no address yet gets no layer. An op that isn’t registered, or a parameter its class refuses, is a 400 with "error", and nothing changes.

POST /api/process (the same two chains) and POST /api/pipeline/apply (the pipeline builder’s nodes) did this before this release. They still answer as they did, with a Deprecation header, and are removed in the next release.
